# GitHub + ServiceNow Workflow — ScholarHub
> Agent: this is the version control system for the team. Follow these steps exactly to avoid merge conflicts across 5 members.

---

## How Studio Source Control Works

ServiceNow Studio stores application files as XML in your GitHub repository. When you commit from Studio, it serializes your tables, scripts, and portal configs into XML files and pushes them to GitHub. The repo structure is managed by ServiceNow — do not manually edit XML files in the repo.

```
Repo structure (auto-generated by ServiceNow):
scholarhub-servicenow/
├── application.properties
├── sn_source_control.properties
└── [application-name]/
    ├── business_rule/
    ├── client_script/
    ├── sys_ui_action/
    ├── sys_script_include/
    ├── sp_widget/
    ├── sp_portal/
    ├── sys_notification/
    ├── wf_activity/     (Flow Designer)
    └── sys_db_object/   (table definitions)
```

## Day 1 Setup (One Time)

### 1. Create GitHub Repository
```
1. Go to github.com → New Repository
2. Name: scholarhub-servicenow
3. Visibility: Private (or Public if team agrees)
4. Initialize: with README
5. Copy the HTTPS URL: https://github.com/[org]/scholarhub-servicenow.git
```

### 2. Create GitHub PAT
```
GitHub → Settings → Developer Settings → Personal Access Tokens → Tokens (classic)
→ Generate new token (classic)
Name: ServiceNow-ScholarHub
Expiration: 90 days (beyond May 23)
Scopes: [x] repo  [x] workflow
→ Generate token
Copy immediately — shown once only
```

### 3. Create ServiceNow Credential
```
Navigate to: /sys_auth_profile_basic_list.do → New
Name: GitHub - ScholarHub PAT
Type: Basic
User name: [your GitHub username]
Password: [paste the PAT token here]
Save
```

### 4. Link Studio to GitHub
```
Open Studio → Source Control → Link to Repository

Repository URL: https://github.com/[org]/scholarhub-servicenow.git
Branch: main
Credential: GitHub - ScholarHub PAT

Click "Link to Repository"
Wait for sync to complete (may take 1-2 minutes)
```

## Daily Workflow (Every Session)

### Start of Session — Pull First
```
Studio → Source Control → Apply Remote Changes
(Always do this before starting work to get teammates' latest changes)
```

### During Work — Commit Often
```
Studio → Source Control → Commit Changes

Best practice: commit after each completed task, not at end of day
Good commit: "feat: add validate_documents business rule"
Bad commit: "updates" or "stuff"
```

### End of Session — Push and Verify
```
Studio → Source Control → Push Changes
Then: open GitHub in browser and confirm your latest commit appears
```

## Branch Strategy for 5 Members

To avoid conflicts, each member works on their own branch:

```
main              ← stable, demo-ready code only
├── feature/m1-backend      ← Member 1: tables, BRs
├── feature/m2-workflow     ← Member 2: Flow Designer, notifications
├── feature/m3-portal       ← Member 3: Service Portal
├── feature/m4-ai           ← Member 4: Integration Hub, AI widget
└── feature/m5-ui-docs      ← Member 5: UI Actions, Client Scripts
```

### Create your branch (Day 1)
```
Studio → Source Control → Create Branch
Name: feature/m[your-number]-[your-area]
Base: main
```

### Merge to main (After testing)
```
On GitHub: Create Pull Request from your branch → main
Team lead reviews → Merge
All members: Apply Remote Changes to get the merged code
```

## Handling Merge Conflicts

If two members edited the same file:

```
1. Apply Remote Changes — Studio will show conflict alert
2. Go to GitHub → your branch → compare with main
3. Identify conflicting files (usually widget or script files)
4. Coordinate with the other member — decide whose version is correct
5. One member re-applies their changes on top of the merged state
6. Commit and push the resolution
```

**Prevention:** Each member owns their files. Don't edit another member's widgets or scripts without coordinating first.

## What to NEVER Commit

```
# .gitignore equivalents — Studio should not commit these:
- API keys or passwords (store in System Properties or Credentials)
- Personal email addresses
- Test data records (these aren't captured by source control anyway)
- System Log entries
- Update Set XML files (keep separately, not in the app repo)

# Verify before every push:
Studio → Source Control → Show Changes
Review the diff — if you see any credential or sensitive value, don't commit
```

---

## Recovery: If Something Breaks After Merge

```
1. Identify the last good commit in GitHub
2. Studio → Source Control → Show Changes → check what's different
3. Option A: Revert specific file
   GitHub → find the file → History → find good version → copy XML → paste back in Studio
4. Option B: Reset to last good commit
   GitHub → commits → find good commit → copy hash
   Studio → Source Control → (if available) Reset to commit [hash]
   WARNING: this discards all work since that commit
```
